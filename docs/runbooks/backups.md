# Backups — DevThread

DevThread stores its only mutable state in a single Postgres database:
`users`, `sessions`, `posts`, `messages`, `subscribers`. MDX articles live in
`content/posts/` and are version-controlled, so they need no backup beyond git.

## Provider
Supabase (free/standard tier). Backups are managed by Supabase, not by us.

## Schedule
| What | Frequency | Retention |
|---|---|---|
| Automated daily full backup | 02:00 UTC | 7 days |
| WAL (point-in-time) archiving | continuous | 24 hours |
| Manual `pg_dump` snapshot | on every deploy | 1, kept in `docs/runbooks/` |

## Restore
### From Supabase console (point-in-time)
1. Open the Supabase dashboard → Database → Backups.
2. Pick a timestamp between the incident and the last good state.
3. Click **Restore** into a **new** database — never restore into production
   directly. Supabase creates a clone, then you promote it.
4. Update `DATABASE_URL` in the production env to point at the restored DB.
5. Redeploy. Verify `/api/health` returns `ok`.

### From a manual `pg_dump` snapshot
```bash
# Dump (run locally, from a machine that can reach the DB):
pg_dump "$DATABASE_URL" -f devthread-$(date +%F).sql

# Restore into a separate database first, then swap:
psql "$TEST_DATABASE_URL" -f devthread-YYYY-MM-DD.sql
```
See `scripts/db-restore-test.sh` — it restores the latest snapshot into a
scratch database so restores are tested without touching production.

## What is NOT backed up
- `public/uploads/` (cover images, avatars). These are regenerated by re-uploading
  through the editor; there is no recovery path for a lost image.
- Session cookies — sessions expire and are recreated on login.

## Test it
Run `scripts/db-restore-test.sh` at least once after any schema change and
record the result in `docs/runbooks/restore-log.md`.
